# 2026-04-17 Cha PT 웹 애플리케이션 장애 사후 분석(Post Mortem)

_[Read this in English 🇬🇧](2026-04-17.md)_

_이 문서는 ChaPT 프로덕션 시스템에서 발생한 2026년 4월 17일 장애에 대한 사후 검토 보고서입니다. 포트폴리오 산출물로 작성되었으며, 책임 추궁 없는(blameless) 관점으로 기술되었습니다. 작성자는 장애 대응자 본인입니다._

ChaPT는 단일 EC2 인스턴스에서 호스팅되는 소규모 예약/분석 웹 애플리케이션입니다(Go + MySQL).

## 핵심 용어(Key Terms)

- **EBS** (Elastic Block Store): AWS의 네트워크 연결형 디스크 서비스입니다. EBS 볼륨은 EC2 인스턴스에 연결된 가상 하드 드라이브로, 이 사례에서는 OS, MySQL, 웹 서버를 모두 담고 있는 단일 루트 볼륨을 의미합니다.
- **gp3**: 현행 범용 EBS 볼륨 유형(SSD)입니다. 기본적으로 125 MiB/s 처리량과 3000 IOPS의 고정 기준치(baseline)를 제공하며, 더 높은 한계를 명시적으로 프로비저닝하지 않는 한 이 기준치를 초과하면 스로틀링이 발생합니다.
- **OOM** (Out Of Memory, 메모리 부족): 시스템이 가용 RAM을 모두 소진한 상태입니다. Linux는 `oom-killer`를 호출하여 메모리를 회수하기 위해 프로세스를 종료함으로써 대응합니다. 이것이 크래시에 대한 초기의 (잘못된) 가설이었습니다.

## 요약 / TL;DR

2026년 4월 17일, ChaPT 웹사이트는 UTC 기준 07:25부터 10:19까지 약 3시간 동안 응답하지 않았습니다. 원인은 사이트 관리자가 내부 분석 대시보드에서 실행한 최적화되지 않은 쿼리들이었으며, 이로 인해 인스턴스 gp3 루트 볼륨의 125 MiB/s 처리량(throughput) 한계가 포화되었습니다. 그 결과로 발생한 I/O 고갈(starvation)은 운영체제 전반으로 연쇄적으로 확산되어 systemd DBus 타임아웃, Docker 헬스 체크 실패, 그리고 인스턴스가 명목상 "running" 상태였음에도 SSH 데몬이 응답하지 않는 상황을 야기했습니다. 복구를 위해서는 새로운 EC2 인스턴스를 프로비저닝하고 Elastic IP를 재할당해야 했으며, 고객 데이터 손실은 없었습니다. 이 장애는 조용한 한계치(silent-ceiling)에 대한 모니터링 공백, 장애 영향 범위(blast-radius) 격리가 없는 공유 볼륨 아키텍처, 그리고 성능 검토를 거치지 않은 관리자 도구라는 일련의 문제를 드러냈습니다. 이후 하드닝 작업으로 각 문제를 해결했습니다.

- 데이터 영향: 없음 - DB 쓰기 손실 없음, DB는 손상이 아니라 오프라인 상태였음

## 근본 원인 분석(Root Cause Analysis)

**관리자 대시보드에서 실행된 최적화되지 않은 쿼리가 볼륨의 조용한 125 MiB/s 처리량 한계를 포화시켜 30분간의 I/O 고갈을 유발했습니다. 스로틀링이 시작된 후 약 20분 이내에 연쇄적인 사용자 영역(userland) 장애(DBus 타임아웃, Docker 헬스 체크 실패, SSH 로그인 멈춤)가 발생하여 인스턴스가 응답 불능 상태가 되었습니다.**

- 4월 17일 07:20 UTC, 사이트 관리자가 내부 분석 대시보드를 열었습니다.
- 해당 페이지는 분석 테이블(58일 가동 기간 동안 누적된 수만 행 규모의 방문자, 세션, 페이지뷰 레코드)에 대해 하나 이상의 집계 쿼리(`GROUP BY`, `COUNT`, 시간 버킷팅)를 실행했습니다.
- 이 쿼리들은 지속적인 읽기 부하를 유발했고, 5분 이내에 인스턴스 gp3 루트 볼륨의 125 MiB/s 기본 처리량 한계를 포화시켰습니다.
- 볼륨이 스로틀링되었고, I/O 큐 깊이가 상승했으며, 20분 이내에 systemd-logind DBus 호출, Docker 헬스 체크, 신규 SSH 연결이 모두 타임아웃되었습니다.
- 인스턴스는 "running" 상태를 유지하며 EC2 인스턴스 상태 검사(EC2 instance status check)를 통과했으나, 사실상 사용자에게 응답하지 못했습니다.
- 약 3시간 후 새 인스턴스를 프로비저닝하고 Elastic IP를 재할당함으로써 서비스가 복구되었습니다.

### 기여 요인(Contributing Factors)

- 급격한 스로틀링 전에 어떠한 경고도 제공하지 않는, 모니터링되지 않는 기본 처리량(125 MiB/s) 한계를 사용한 gp3 볼륨
- 단일 볼륨 아키텍처(MySQL, Go 웹 서버, OS가 하나의 8 GB 루트 볼륨을 공유)로 인해 느린 쿼리 하나가 전체 시스템을 막을 수 있었음
- 로그 로테이션 또는 쿼리 시간(query-time) 모니터링 부재
- `VolumeThroughputExceededCheck`, CPU, 인스턴스 상태에 대한 알람 부재
- CloudWatch 에이전트 미설치 - 메모리 및 디스크 공간 가시성 부재
- 분석 대시보드가 인덱스 없고 페이지네이션 없는 집계 쿼리를 실행
- 긴 가동 시간(58일) 동안 정기 부하 테스트 없이 테이블이 스캔 가능한 임계치를 넘어 증가함

### 신속한 진단을 방해한 요인(Factors Impeding Speedy Diagnosis)

- 초기 가설은 OOM이었음 - 크래시 부팅의 systemd 저널에서 `oom-killer`를 grep하여 0건임을 확인한 후에야 배제됨
- CloudWatch 에이전트가 설치되지 않아 CloudWatch에 메모리 및 디스크 메트릭이 없었음
- 장애 내내 EC2 인스턴스 상태 검사가 통과하여 심각성을 가림
- I/O 고갈은 가시적인 오류가 아니라 조용한 느려짐으로 나타남 - 익숙하지 않은 패턴

## 해결(Resolution)

- 복구는 두 단계로 진행되었습니다.
  1. 첫째, 죽은 인스턴스의 루트 볼륨을 스냅샷으로 보존(포렌식 증거 보존)한 뒤 분리(detach)했습니다.
  2. 둘째, 동일한 가용 영역에 새로운 t3.small 인스턴스를 프로비저닝하고 Docker 및 Docker Compose를 구성한 후, 새 `.env` 파일과 함께 `git clone && docker compose up -d`로 애플리케이션 스택을 재배포했습니다. 기존 Elastic IP를 새 인스턴스에 재연결하여 DNS 변경 없이 서비스를 복구했습니다.
- 고객 데이터 손실은 없었습니다 — 장애 이전에 누적된 분석 레코드는 중요하지 않아 복원하지 않았습니다.
- 새 인스턴스는 긴급 복구 중 처음에 t3.small로 프로비저닝되었으나, 이번 장애가 RAM이나 CPU에 의한 것이 아님을 분석으로 확인한 후 다시 t3.micro로 다운사이징되었습니다. MySQL 메모리 설정은 1 GB 인스턴스 크기에 맞게 튜닝되었습니다. 이후 하드닝 작업으로 근본적인 gp3 처리량 노출 문제를 해결했습니다.

## 잘된 점(What Went Well)

- Elastic IP 덕분에 EC2 인스턴스 간 매끄러운 전환이 가능했습니다. 복구에 DNS 존 파일 변경이 필요하지 않았습니다.
- 죽은 볼륨의 EBS 스냅샷이 복구 작업을 막지 않으면서 포렌식 증거를 보존했습니다.
- Docker Compose 덕분에 새 인스턴스에서의 애플리케이션 재배포가 훨씬 수월했습니다.
- 죽은 볼륨의 systemd 저널이 온전히 보존되어 사후에 연쇄 장애를 정확히 재구성할 수 있었습니다.
- `VolumeThroughputExceededCheck` 메트릭이 CloudWatch에 존재했기에, 무엇을 봐야 하는지 알게 된 순간 AWS가 이미 증거를 기록해 두고 있었습니다.

## 미흡했던 점(What Went Poorly)

- 핵심 메트릭에 대한 사전 모니터링 부재. `VolumeThroughputExceededCheck`는 처리량 포화를 직접 알려주지만, 알람이 설정된 적이 없었습니다. 사전 모니터링이 있었다면 진단이 훨씬 빨랐을 것입니다.
- 백업이 존재하지 않았습니다. 죽은 볼륨이 복구 불가능했다면 58일치 분석 데이터를 잃었을 것입니다.
- 진단이 처음에 잘못된 가설을 쫓았습니다. 저널 증거(`oom-killer` 항목 없음)가 I/O 고갈로 방향을 바로잡아 주기 전까지 약 30분을 OOM 이론에 소비했습니다.
- 런북(runbook)이 존재하지 않았습니다. 모든 복구 단계가 즉흥적이었습니다. 문서화된 절차가 있었다면 3배 빠르고 위험도 낮았을 것입니다.
- 관리자 도구가 성능 검토를 받지 못했습니다. 분석 페이지는 현실적인 데이터 규모에서 부하 테스트를 한 적이 없어, 테이블이 커지면서 "안전"에서 "위험"으로 조용히 넘어갔습니다.
- 모든 서비스가 하나의 8 GB 루트 볼륨에 함께 배치되었습니다. 어느 하나의 느린 쿼리가 나머지 전부를 고갈시킬 수 있었고 — 실제로 그렇게 되었습니다.

## 배운 점(Lessons Learned)

1. **gp3 한계치는 조용하다.**
   - gp3는 gp2의 버스트 크레딧 실패 모드를 해결하지만, 자체적으로 보이지 않는 처리량(125 MiB/s) 및 IOPS(3000) 한계를 도입합니다.
   - 한계에 접근해도 기본 알람이 울리지 않습니다.
   - 기본 gp3 위의 I/O 민감 워크로드는 더 높은 한계를 프로비저닝하거나 `*ExceededCheck` 메트릭에 대한 명시적 모니터링이 필요합니다.

2. **내부 도구도 프로덕션이다.**
   - 분석 대시보드는 "나만 쓰는 것"이었기에 사용자 대면 경로에 적용되는 성능 검토를 전혀 받지 못했습니다.
   - 그러나 동일한 데이터베이스, 디스크, 인스턴스를 공유했기에 느린 관리자 쿼리는 느린 사용자 쿼리와 구별되지 않았습니다.
   - 관리자 도구도 공개 표면과 동일한 기준을 충족해야 합니다.

3. **긴 가동 시간은 느린 증가를 숨긴다.**
   - 1주차에 안전한 쿼리가 8주차에는 치명적일 수 있습니다.
   - 정기적인 부하 테스트나 쿼리 감사가 없으면, 그 전환은 터지기 전까지 보이지 않습니다.

4. **인프라가 "정상"인 것 ≠ 애플리케이션이 정상인 것.**
   - EC2 인스턴스 상태 검사는 장애 내내 통과했습니다.
   - 앱/인프라 경계를 넘는 메트릭(`VolumeThroughputExceededCheck`)만이 현실을 포착했습니다.
   - 외부 합성 모니터링은 타협 불가능한 필수 요소입니다.

5. **복구 시간은 설계 매개변수다.**
   - 런북과 코드형 인프라(IaC)의 부재가 5분짜리 문제를 수 시간짜리 문제로 만들었습니다.
   - 복구 능력은 가정하는 것이 아니라 명시적으로 설계해야 합니다.

## 결론(Conclusion)

이 장애는 궁극적으로 검토되지 않은 관리자 페이지에서의 단 한 번의 클릭으로 인해 발생했습니다. 그 취약성 — 어느 한 사람의 일상적인 동작이 전체 프로덕션 시스템을 포화시킬 수 있었다는 점 — 이 진정한 발견이었습니다. 구체적인 수정(gp3 처리량 상향, 쿼리 최적화)은 증상을 다루는 것이고, 시스템적 수정(장애 영향 범위 격리, 한계치 모니터링, 관리자 도구를 프로덕션으로 취급)은 원인을 다루는 것입니다.
